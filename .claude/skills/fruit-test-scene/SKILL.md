# 과일 장면으로 계산식 테스트하기

계산식은 폰 없이 검증해야 한다. 그래서 정답을 알고 있는 가짜 과일 장면을 만들고, 계산식이 그 정답을 다시 찾아내는지 본다. 좌표 규칙을 하나만 틀려도 결과가 그럴듯하게 틀리므로, 좌표를 다루기 전에 `references/coordinates.md`를 읽는다.

## 순서

1. **무엇을 확인할지 정한다**: 입력(윤곽 시선 또는 사진), 출력(가로·세로·거리), 허용 오차.
2. **정답을 독립적으로 만든다**: 테스트할 계산식과 같은 식으로 정답을 만들지 않는다(같은 실수를 하면 함께 맞아 버린다).
   - 윤곽 시선: 시선이 과일에 닿는지를 이차방정식으로 판정하고, 닿음과 안 닿음이 바뀌는 각도를 이분법으로 찾는다(`test/measure.test.js`의 `spheroidSilhouette`).
   - 사진: 화소마다 시선을 쏘아 과일·테이블과 만나는 점의 색을 칠한다(`test/scene.js`의 `render`).
   - 거리 정답: 카메라에서 과일 중심을 향한 선이 표면과 만나는 점까지(`trueSpheroidDistanceMm`).
3. **기본 장면부터 어려운 장면까지 넣는다**(아래 「장면 옵션」).
4. **실행한다**: `node test/measure.test.js`, `node test/detect.test.js`, `node test/app-flow.test.js`
5. **통과해도 숫자를 본다**: 처음부터 전부 통과하면 테스트가 너무 쉬울 수 있다.
   - 실제 오차(측정값/정답)를 한 번 찍어 허용 오차보다 충분히 작은지 확인한다.
   - 값이 정말 구분되는지 확인한다. 예: 비율을 틀리게 넣었을 때의 맞춤 오차가 화소 1개의 각도(약 1/fx 라디안)보다 커야 그 비율을 사진에서 찾을 수 있다. 작으면 그 조건(각도·거리)은 앱에서 막거나 안내한다.
   - 확인용 출력은 테스트에 남기지 않는다.
6. **실패 조건도 테스트한다**: 계산하면 안 되는 입력이 `null`이나 오류(`none`, `cut`, `small`)로 끝나는지 본다.

## 예시

[예시] 「AR에서 지름 70mm 과일을 45도로 보면 크기와 거리가 3% 안에서 다시 나온다」를 확인하는 테스트

```js
test("AR 45도: 크기·거리 3% 이내", () => {
  const opt = spheroidArScene(0.035, 0.035, 45, { noise: 8, shadow: true }); // 입력: 정답을 아는 장면
  const found = detectFruitSpheroid(render(opt), seedFor(opt), opt.k, opt.pose);
  const cam = [opt.pose[12], opt.pose[13], opt.pose[14]];
  const m = measureSpheroidCone(found.cone, found.s, cam, 0);              // 출력: 계산한 크기·거리
  assert.ok(relErr(m.widthMm, 70) < 0.03, `크기 ${m.widthMm.toFixed(1)}mm`);
  assert.ok(relErr(m.distanceMm, trueSpheroidDistanceMm(opt)) < 0.03);     // 정답은 계산식과 따로 구함
});
```

출력 예: `ok   AR 45도: 크기·거리 3% 이내`. 처음 통과하면 실제 값(예: 「크기 69.8/70.0」)을 한 번 찍어 본 뒤 그 출력은 지운다.

## 장면 옵션 (`render(opt)`, test/scene.js)

| 옵션 | 뜻 | 쓰는 이유 |
|---|---|---|
| `center`, `r`, `rc` | 과일 중심(m), 가로 반지름, 세로 반지름(없으면 `r`과 같아 구) | 과일은 테이블 위에 놓이므로 `center[1] = rc` |
| `pose` | `cameraPose(위치, 내려다보는 각도)`로 만든 카메라 → 세계 행렬 | 비스듬히 본 장면 |
| `k` | 초점거리·중심 `{ fx, fy, cx, cy }`(px) | AR은 약 480, 근거리 사진은 약 520 |
| `noise` | 화소 잡음 크기 | 실제 카메라 잡음 |
| `shadow` | 과일 옆 테이블 그림자 | 경계를 잘못 찾게 만듦 |
| `highlight` | 과일 위 반사광 | 과일 안에서 경계로 착각 |
| `stem` | 꼭지(어두운 점) | 과일 안에서 경계로 착각 |
| `blob` | 과일 옆에 붙은 과일색 물체 | 윤곽이 끊겨 경계점이 새어 나감 |
| `other` | 옆에 놓인 다른 과일 `{ center, r, color }` | 화면 가운데에 가까운 과일을 고르는지 |
| `table`, `fruit` | 테이블·과일 색 | 나무색 테이블 등 |
| `seedShift` | 가리킨 지점을 과일 가운데에서 비킴 | 사용자가 정확히 겨누지 않음 |

이미 있는 장면 함수: `photoScene`(약 10cm 근거리), `arScene`(30cm 이상, 구), `spheroidArScene(a, c, 기운 각도)`(30cm 이상, 회전타원체)

### 여러 위치에서 본 장면 (다가가며 크기 정하기)

크기는 다가가는 동안 여러 위치에서 본 윤곽으로 정하므로, 한 장이 아니라 **경로**를 만든다.

| 함수 | 파일 | 만드는 것 |
|---|---|---|
| `approachPath(center, 기울기, from, to, n, side)` | measure.test.js | 과일 쪽으로 곧장(또는 옆으로 흔들며) 다가가는 카메라 위치 n개 |
| `viewsAlong(path, center, a, c)` | measure.test.js | 위치마다 정확한 윤곽 시선을 원뿔로 맞춘 `{ origin, d, sinA }` |
| `approachFrames(r, 기울기, from, to, n, extra)` | scene.js | 다가가는 동안 찍힌 사진 n장(손떨림으로 각도·위치가 조금씩 바뀜) |
| `sizeFromFrames(frames)` | detect.test.js | 사진마다 인식 → 원뿔을 세계 좌표로 바꿔 `fitSphereViews`로 크기 계산 |

- **꼭 넣을 경우**: 곧장 다가감(크기 변화만 있음), 옆으로 흔들며 다가감(시차), 거의 바로 위에서 다가감, 폰이 거의 안 움직임(크기를 정하지 않아야 함), 위치가 너무 적음
- **납작한 과일**: 구로 보므로 비스듬히 볼수록 조금 작게 나온다(납작 15%면 10~60도에서 80 → 75mm). 정확한 값 대신 「세로와 가로 사이, 각도에 따른 차이 6% 이내」를 본다
- **앱 흐름까지 볼 때**: `test/app-flow.test.js`는 app.js를 가짜 화면 요소로 불러, 장면을 카메라 이미지로 돌려주는 가짜 AR 프레임을 넣는다. 화면 요소의 처음 상태(index.html의 `hidden`)를 맞춰 두지 않으면 앱 문제가 아닌데 실패한다
- **얼마나 움직여야 하는지**: 이동 거리를 바꿔 가며 오차를 찍어 본다. 잡음과 그림자를 넣은 장면에서는 7cm만 움직여도 1% 안쪽이었다(실제 AR 위치 오차는 폰에서 확인)

## 허용 오차 기준

| 입력 | 허용 오차 | 이유 |
|---|---|---|
| 정확한 윤곽 시선 | 0.5~1% (구 결과와 비교할 때는 1e-6) | 계산식 자체의 오차만 남음 |
| 계산으로 그린 사진(잡음 없음) | 1% | 화소 단위로 경계를 찾는 오차 |
| 잡음·그림자·반사광·끊김 | 2~3% | 튀는 점을 버린 뒤 남는 오차 |

## 자주 나오는 경우

- **새 모양 모델로 바꿀 때**(예: 구 → 회전타원체): 예전 모델과 같아지는 조건(가로=세로)에서 예전 함수와 결과가 같은지(1e-6) 먼저 테스트한다. 그래야 기존 기능이 그대로임을 보장한다.
- **바로 위에서 본 장면**: 세로가 윤곽에 드러나지 않는다. 세로를 맞히는지 보지 말고, 기운 각도가 작게 나와 걸러지는지를 본다.
- **테스트 파일의 줄바꿈**: 저장소 파일은 CRLF일 수 있다. 문자열을 바꿔 끼우는 스크립트로 고칠 때는 줄바꿈을 맞춘다.
