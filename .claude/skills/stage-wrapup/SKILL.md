# 단계 마무리

todo의 단계는 「구현 → 테스트 통과 → 체크 → 커밋·push → 사용자 확인 → 다음 단계」로 진행한다. 이 스킬은 구현이 끝난 뒤부터 사용자 확인을 받기까지를 맡는다. 완료의 기준은 코드를 다 쓴 것이 아니라 **테스트를 통과한 것**이다.

## 순서

1. **테스트 실행**: 저장소 맨 위에서 아래 두 명령이 모두 「모두 통과」로 끝나야 한다.
   ```
   node test/measure.test.js
   node test/detect.test.js
   ```
   - 실패하면 고친 뒤 다시 실행한다. 원인이 이번 단계 밖에 있으면 고치기 전에 todo에 `[버그 수정]` 항목을 추가한다(3번).
   - 새 계산식의 테스트를 쓰거나 결과가 너무 쉽게 통과하면 `fruit-test-scene` 스킬을 따른다.
2. **todo 체크**: 테스트로 확인한 할 일만 `[ ]` → `[x]`로 바꾼다.
   - `[폰]` 항목은 사용자가 폰에서 확인하므로 체크하지 않는다.
   - 할 수 없었거나 일부만 한 항목은 체크하지 않고, 보고할 때 이유를 말한다.
3. **변경 표시**: 처음 계획 뒤에 todo나 PRD가 바뀌었으면 표시한다(아래 「변경 표시 규칙」).
4. **표시 검사**: 아래 명령을 실행해 문제가 없을 때까지 고친다.
   ```
   node .claude/skills/stage-wrapup/scripts/check-marks.js
   ```
   - 커밋 전에는 이번에 새로 쓴 changes.md 항목의 「커밋 번호가 비어 있음」만 남아도 된다. 커밋한 뒤 6번에서 채운다.
5. **커밋·push**: 「커밋 메시지」 형식으로 커밋하고 push한다. 사용자가 커밋을 맡겼을 때만 한다.
6. **커밋 번호 기록**: 이번 커밋에 들어간 changes.md 항목의 「날짜 / 커밋」에 커밋 번호(앞 7자리)를 적는다. 이 수정은 다음 커밋에 함께 넣는다.
7. **보고**: 사용자에게 아래를 알린다. 사용자가 확인하기 전에는 다음 단계를 시작하지 않는다.
   - 끝낸 할 일 번호(예: 「14-1~14-7 완료」)와 각각 무엇을 했는지
   - 테스트 결과(통과 개수, 실제 오차처럼 숫자로 확인한 것)
   - 체크하지 않은 항목과 이유
   - `[폰]` 항목: 무엇을, 어떤 순서로, 무엇과 비교해 확인할지

## 변경 표시 규칙

처음 계획한 todo·PRD에서 바뀐 것은 바뀐 줄 끝에 표시하고, 자세한 내용은 `changes.md`에 번호(`C-n`)를 붙여 한 곳에 모은다.

- **표시 형식**: `(구분 · 요약 / [changes.md C-n](changes.md#c-n))`
  - todo 할 일은 PRD 근거 괄호 뒤, 줄 맨 끝에 붙인다.
  - 새로 붙인 단계는 단계 제목에 한 번만 붙인다. 그 단계 안에서 생긴 버그·변경은 항목마다 따로 붙인다.
  - 한 변경이 여러 줄에 걸치면 같은 C-번호를 가리킨다.
- **구분**: `추가`(새 할 일, 버그 수정 포함) · `변경`(계획한 할 일이나 PRD 내용을 고침) · `취소`(하지 않기로 함. 지우지 않고 `~~취소선~~`으로 남김)
- **요약**: changes.md 맨 위 「요약에 쓰는 말」에서 고른다. 맞는 말이 없으면 목록에 먼저 추가한다.
- **표시하지 않는 것**
  - 이전 단계에서 못 끝낸 항목을 이번에 끝내는 것(진행일 뿐이다. 내용을 고쳐서 하면 `변경`)
  - PRD의 문구 다듬기·세부 보충. PRD는 핵심 기능(4번), 만들지 않는 것(5번), 기술 조건의 방향(7번), 완성 기준(10번)이 바뀔 때만 표시한다.
- **changes.md 기록**: 목록 표에 한 줄(`| [C-n](#c-n) | 구분 | 요약 | 대상 |`)을 넣고, 아래 상세에 `assets/change-entry.md` 양식으로 항목을 쓴다. 시행착오(처음 시도한 방법과 버린 이유)는 짧게라도 남긴다.
- **PRD 근거가 없는 할 일**(개발 도구 등)은 todo의 「추가 제안」 칸에 `제안-n` 번호로 넣는다.

## 커밋 메시지

```
종류: 무엇을 했는지 (todo 번호)

왜 했는지 1~3문장.

- 무엇을 바꿨는지 항목별로 (해당 todo 번호)
- 테스트 결과

Co-Authored-By: (함께 작업한 AI)
```

- 종류: `feat`(기능) · `fix`(버그 수정) · `docs`(문서) · `test`(테스트만) · `chore`(정리)
- 제목만 읽어도 무엇을 했는지 알 수 있게 쓴다. 「수정」, 「업데이트」만 쓰지 않는다.
- todo 번호는 범위로 쓴다: `(todo 14-1~14-7)`, `(todo 제안-1)`

[예시]
```
feat: AR에서 과일 가로·세로 크기 측정 (todo 14-1~14-7)

만감류는 위아래로 납작해 지름 하나로는 크기를 다 나타내지 못한다.
폰을 비스듬히 든 채 한 번에 가로·세로를 잰다.

- 회전타원체를 구로 바꿔 계산하는 변환과 비율 찾기 (14-1, 14-2)
- 테스트: 납작한·길쭉한 과일 사진에서 가로·세로·거리 3% 이내 (14-6)
```

## 자주 나오는 경우

- **테스트 중 버그 발견**: 바로 고치지 말고 먼저 todo에 `- [ ] n-m. [P?] [버그 수정] 증상 (PRD #근거) (추가 · 버그 / C-n)`을 넣고 changes.md에 기록한 뒤 고친다.
- **계획한 테스트 방법을 쓸 수 없음**(예: 브라우저를 열 수 없음): 다른 방법으로 확인했으면 그 사실을 보고하고, 계획과 달라진 점은 `변경`으로 표시한다. 확인하지 못했으면 체크하지 않는다.
- **단계가 길어짐**: 중간에 한 번 더 커밋·push해도 된다. 여러 단계를 한 커밋에 몰지는 않는다.
- **`[폰]` 확인에서 문제가 나옴**: 사용자가 알려준 증상을 `[버그 수정]` 항목으로 추가하고, 같은 단계 안에서 고친다.
