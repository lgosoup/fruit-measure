# fruit-measure

만감류(한라봉·천혜향 등)의 근적외선 당도 측정을 돕는 폰 웹앱입니다. 과일을 화면 가운데 두고 다가가기만 하면 앱이 과일을 찾아 따라가며 **크기(지름)**를 재고, 이어서 **카메라\~과일 표면 거리**를 실시간으로 보여 주며 측정 거리(12cm 이내)로 안내합니다. 12cm 안에서 폰을 잠시 멈추면 자동으로 촬영하고 그 순간의 거리를 기록합니다. 바이브 코딩(PRD → Todo → 테스트 → 스킬)으로 만들었습니다.

**바로 사용하기(갤럭시 Z 플립6 크롬): https://lgosoup.github.io/fruit-measure/**

## 1. 제작한 것 소개

### 왜 만들었나

이 앱은 캡스톤 프로젝트 「스마트폰 카메라 결합형 저비용 비파괴 당도 추정 기반 만감류 수확 적기 판정 보조기」에서 **측정 거리와 과일 크기**를 맡는 부분입니다.

- 캡스톤은 만감류에 근적외선을 비추고, 과일 속을 거쳐 돌아온 빛을 값싼 멀티스펙트럼 센서로 재서 자르지 않고 당도를 추정합니다.
- 시중 비파괴 당도계는 센서를 과일에 붙여 재지만, 캡스톤은 붙이지 않고 신호가 희석되지 않는 가까운 거리(최대 12cm)에서 잽니다. 그래서 **센서와 과일 사이 거리**가 측정값을 바꾸고, 측정한 순간의 거리를 함께 기록해 보정해야 합니다.
- **과일 크기**는 빛이 과육을 지나는 길이를 바꾸는 보정 값입니다. 당도를 직접 알려 주는 값이 아니므로 같은 방법으로 일관되게 잰 지름 하나면 됩니다.
- 지금은 캘리퍼스로 크기를, 자로 거리를 하나씩 재고 손으로 적어야 합니다. 이 앱은 폰 하나로 둘을 재고 기록합니다. **앱에서 촬영하는 순간이 근적외선을 비추고 재는 순간**에 해당합니다(센서 연동은 이후 캡스톤에서 합니다).

### 사용 방법

1. 과일을 테이블 위에 놓고 「측정 시작」을 누릅니다. 카메라 권한을 허용합니다.
2. 30cm쯤 떨어져 과일을 화면 가운데에 둡니다. 앱이 화면 가운데에 가장 가까운 과일을 찾아 둘레에 원을 그리고 따라갑니다. 다른 물체를 잡았으면 「다시 선택하기」를 누릅니다.
3. 과일 쪽으로 천천히 다가갑니다. 여러 위치에서 본 윤곽으로 크기가 정해지면 화면 옆에 완료 표시와 지름(mm)이 뜹니다.
4. 계속 다가가면 화면 아래에 「표면까지 ○○ cm」가 실시간으로 나오고 「촬영하려면 n cm 더 가까이」로 안내합니다. 12cm 안에 들어오면 초록색으로 바뀌고 진동으로 알립니다. 너무 가까워 과일이 화면에 다 안 들어오면 「조금 멀리」로 안내합니다.
5. 12cm 안에서 폰을 잠시(약 0.5\~1초) 멈추면 자동으로 촬영됩니다. 흔들리면 「폰을 잠시 멈춰 주세요」가 뜹니다. 「자동 촬영: 끔」으로 바꾸면 「촬영」 버튼으로 직접 찍습니다.
6. 찍은 사진에서 과일 윤곽과 카메라\~과일 표면 거리(mm)가 나옵니다. 윤곽이 틀리면 과일을 터치해 다시 찾거나 「직접 지정」으로 과일 양 끝을 터치합니다. 두 손가락으로 확대·이동할 수 있습니다.
7. 「기록 저장」을 누르면 다음 과일을 잴 수 있도록 AR 화면으로 돌아갑니다. 「기록 보기」에서 목록을 보고 삭제할 수 있습니다.

### 측정 원리

- **과일 찾기·따라가기**: 화면 가운데와 그 둘레 몇 곳에서 과일 윤곽을 찾아, 화면 가운데에 가장 가까운 것을 고릅니다(사용자에게 보이지 않는 기준점). 이후에는 직전 위치에서 다시 찾고, 크기나 위치가 갑자기 크게 바뀌면 다른 물체로 보고 버립니다. 위에서 내려다보면 화면 가운데가 꼭지라서, 찾은 윤곽을 감싸는 더 큰 윤곽이 있고 안쪽이 더 어두우면(꼭지) 바깥을 과일로 고릅니다.
- **윤곽 인식**: 가리킨 지점에서 120개 방향으로 선을 뻗어 과일 색과 달라지는 첫 지점(경계점)을 찾습니다. 과일은 구라서 윤곽을 지나는 시선은 모두 「카메라→과일 중심」 축과 같은 각도를 이룹니다(원뿔). 경계점을 이 원뿔에 맞추면서 맞지 않는 점은 버리므로, 윤곽 일부가 끊기거나 그림자·반사광이 있어도 둥근 윤곽을 찾습니다.
- **크기(다가가며)**: AR은 프레임마다 폰의 위치와 자세를 알려 줍니다. 여러 위치에서 본 윤곽 원뿔을 모아 하나의 구(중심, 반지름)에 최소제곱으로 맞추면 지름이 나옵니다. 폰이 5cm 이상 움직이고 3곳 이상에서 본 뒤, 최근 값 5개가 2% 안으로 모이면 크기를 확정합니다. 폰을 드는 각도나 테이블 높이를 가정하지 않습니다.
- **거리**: 크기를 알면 화면 속 윤곽 원뿔의 각도만으로 거리가 나옵니다. 원뿔 반각을 α라 하면 `중심까지 거리 = 반지름 / sin α`이고, 여기서 반지름을 빼면 표면까지 거리입니다. 근거리에서 흔히 쓰는 단순 비례식(초점거리 × 지름 ÷ 사진 속 지름)은 10cm에서 약 5% 짧게 나와 쓰지 않았습니다. 거리는 카메라 이미지와 크기만으로 구하므로, 가까이서 AR이 폰 위치를 놓쳐도 계속 나옵니다.
- **자동 촬영**: 12cm 안에 들어온 뒤의 거리 값 10개가 5mm 안쪽으로 모이면 「안정」으로 보고 그 순간을 찍습니다. 촬영한 사진에서는 AR에서 따라가던 원과 크기가 맞는 윤곽만 골라 거리를 다시 잽니다.

### 알아둘 점

- ARCore를 지원하는 안드로이드 크롬(갤럭시 Z 플립6에서 확인)에서만 동작합니다. PC에서는 첫 화면에 안내만 나오므로 동작은 [실행 영상](#-실행-영상)으로 확인합니다.
- 가까이 다가가면 카메라 화면이 흐려집니다. 웹(WebXR)에서는 AR 카메라 초점을 바꿀 수 없기 때문입니다(설치형 앱이면 가능). 윤곽으로 재는 거리·크기에는 영향이 없어 그대로 두었습니다.
- 크기는 AR이 알려 준 폰 위치로 계산하므로, AR이 위치를 잘못 잡으면(특히 시작 직후) 크기가 크게 틀릴 수 있습니다. [실행 영상](#-실행-영상) 앞부분(0:08)에서도 한 번 100.5mm(실제 약 50mm)가 나왔고, 「크기 다시 재기」로 다시 재 49.1mm를 얻었습니다. 크기가 이상하면 다시 잽니다.
- 아주 가까이 가서 과일을 놓치면 다시 잡지 못하고 계속 놓칠 수 있습니다. 조금 떨어지거나 「다시 선택하기」·「다시 찍기」로 다시 시작합니다.
- 기록은 사용하는 기기의 브라우저에만 저장됩니다. 서버나 계정이 없고, 브라우저의 사이트 데이터를 지우면 기록도 사라집니다. 실습 과제 때 카드 기준으로 잰 기록은 거리 칸이 「–」입니다.

### 기술

HTML, CSS, JavaScript와 WebXR(크롬이 ARCore로 AR 실행)을 사용했습니다. 빌드나 외부 라이브러리는 없고, GitHub Pages로 배포합니다.

## 4. Todo 리스트의 변경 내역

원래 Todo는 **실습 과제를 마쳤을 때의 1\~13단계**입니다. 그 뒤에 바뀌거나 새로 넣은 것은 todo·PRD의 해당 줄 끝(새 단계는 단계 제목)에 굵게 표시했습니다.

```
- [x] 17-12. [P1] [버그 수정] 위에서 찍으면 사진에서 꼭지를 과일로 잡아 … (PRD #4-1, #4-3) **(추가 · 버그 / changes.md C-13)**
```

- 구분: **추가**(새 할 일, 버그 수정 포함) · **변경**(계획한 할 일이나 PRD 내용을 고침) · **취소**(하지 않기로 함, todo에서 지우지 않고 취소선으로 남김)
- 요약: 버그 · 테스트 중 발견 · 생각 못 한 구현 문제 · 새 아이디어 · 범위 조정 · 계획 누락
- 표시의 `C-n`은 [changes.md](changes.md)의 항목으로 연결됩니다. 거기에 원래 내용 → 바뀐 내용, 이유, 시행착오, 날짜·커밋이 있습니다.

# 단계 마무리

todo의 단계는 「구현 → 테스트 통과 → 체크 → 커밋·push → 사용자 확인 → 다음 단계」로 진행한다. 이 스킬은 구현이 끝난 뒤부터 사용자 확인을 받기까지를 맡는다. 완료의 기준은 코드를 다 쓴 것이 아니라 **테스트를 통과한 것**이다.

## 순서

1. **테스트 실행**: 저장소 맨 위에서 아래 세 명령이 모두 「모두 통과」로 끝나야 한다(계산식, 윤곽 인식, AR 화면 흐름).
   ```
   node test/measure.test.js
   node test/detect.test.js
   node test/app-flow.test.js
   ```
   - 실패하면 고친 뒤 다시 실행한다. 원인이 이번 단계 밖에 있으면 고치기 전에 todo에 `[버그 수정]` 항목을 추가한다(3번).
   - 새 계산식의 테스트를 쓰거나 결과가 너무 쉽게 통과하면 `fruit-test-scene` 스킬을 따른다.
2. **todo 체크**: 테스트로 확인한 할 일만 `[ ]` → `[x]`로 바꾼다.
   - `[폰]` 항목은 사용자가 폰에서 확인하므로 체크하지 않는다.
   - 할 수 없었거나 일부만 한 항목은 체크하지 않고, 보고할 때 이유를 말한다.
3. **변경 표시**: 처음 계획 뒤에 todo나 PRD가 바뀌었으면 표시한다(아래 「변경 표시 규칙」).
4. **표시 검사**: `scripts/check-marks.js`를 실행해 문제가 없을 때까지 고친다. 저장소 맨 위에서 실행한다.
   ```
   node .claude/skills/stage-wrapup/scripts/check-marks.js
   ```
   - 검사하는 것: 표시 형식과 굵게 쓰기, 구분·요약 말, C-번호와 링크, changes.md 목록과 상세의 짝, 이유·커밋 번호 빈칸, 취소선
   - 커밋 전에는 이번에 새로 쓴 changes.md 항목의 「커밋 번호가 비어 있음」만 남아도 된다. 커밋한 뒤 6번에서 채운다.
5. **커밋·push**: 「커밋 메시지」 형식으로 커밋하고 push한다. 사용자가 커밋을 맡겼을 때만 한다.
6. **커밋 번호 기록**: 이번 커밋에 들어간 changes.md 항목의 「날짜 / 커밋」에 커밋 번호(앞 7자리)를 적는다. 이 수정은 다음 커밋에 함께 넣는다.
7. **보고**: 사용자에게 아래를 알린다. 사용자가 확인하기 전에는 다음 단계를 시작하지 않는다.
   - 끝낸 할 일 번호(예: 「14-1~14-7 완료」)와 각각 무엇을 했는지
   - 테스트 결과(통과 개수, 실제 오차처럼 숫자로 확인한 것)
   - 체크하지 않은 항목과 이유
   - `[폰]` 항목: 무엇을, 어떤 순서로, 무엇과 비교해 확인할지. 「앱을 새로고침한 뒤」 시작해 달라고 함께 적는다(배포 파일이 10분 캐시됨)
   - `[AI 검토]` 항목은 `pages-preview` 스킬로 배포 페이지를 직접 열어 확인한다

## 변경 표시 규칙

처음 계획한 todo·PRD에서 바뀐 것은 바뀐 줄 끝에 표시하고, 자세한 내용은 `changes.md`에 번호(`C-n`)를 붙여 한 곳에 모은다.

- **원래 Todo**는 실습 과제를 마쳤을 때의 1~13단계다. 그 뒤에 바뀐 것만 표시한다.
- **표시 형식**: `**(구분 · 요약 / [changes.md C-n](changes.md#c-n))**` — 다른 괄호(PRD 근거 등)와 구분되도록 굵게 쓴다
  - todo 할 일은 PRD 근거 괄호 뒤, 줄 맨 끝에 붙인다.
  - 새로 붙인 단계는 단계 제목에 한 번만 붙인다. 그 단계 안에서 생긴 버그·변경은 항목마다 따로 붙인다.
  - 한 변경이 여러 줄에 걸치면 같은 C-번호를 가리킨다.
- **구분**: `추가`(새 할 일, 버그 수정 포함) · `변경`(계획한 할 일이나 PRD 내용을 고침) · `취소`(하지 않기로 함. 지우지 않고 `~~취소선~~`으로 남김)
- **요약**: changes.md 맨 위 「요약에 쓰는 말」에서 고른다. 맞는 말이 없으면 목록에 먼저 추가한다.
- **표시하지 않는 것**
  - 이전 단계에서 못 끝낸 항목을 이번에 끝내는 것(진행일 뿐이다. 내용을 고쳐서 하면 `변경`)
  - PRD의 문구 다듬기·세부 보충. PRD는 핵심 기능(4번), 만들지 않는 것(5번), 기술 조건의 방향(7번), 완성 기준(10번)이 바뀔 때만 표시한다.
- **changes.md 기록**: 목록 표에 한 줄(`| [C-n](#c-n) | 구분 | 요약 | 대상 |`)을 넣고, 아래 상세에 `assets/change-entry.md` 양식으로 항목을 쓴다. 시행착오(처음 시도한 방법과 버린 이유)는 짧게라도 남긴다.
- **PRD 근거가 없는 할 일**(개발 도구 등)은 todo의 「추가 제안」 칸에 `제안-n` 번호로 넣는다.

## 자주 나오는 경우

- **테스트 중 버그 발견**: 바로 고치지 말고 먼저 todo에 `- [ ] n-m. [P?] [버그 수정] 증상 (PRD #근거) **(추가 · 버그 / C-n)**`을 넣고 changes.md에 기록한 뒤 고친다.
- **계획한 테스트 방법을 쓸 수 없음**(예: 브라우저를 열 수 없음): 다른 방법으로 확인했으면 그 사실을 보고하고, 계획과 달라진 점은 `변경`으로 표시한다. 확인하지 못했으면 체크하지 않는다.

# 과일 장면으로 계산식 테스트하기

계산식은 폰 없이 검증해야 한다. 그래서 정답을 알고 있는 가짜 과일 장면을 만들고, 계산식이 그 정답을 다시 찾아내는지 본다. 좌표 규칙을 하나만 틀려도 결과가 그럴듯하게 틀리므로, 좌표를 다루기 전에 `references/coordinates.md`를 읽는다.

## 순서

1. **무엇을 확인할지 정한다**: 입력(윤곽 시선 또는 사진), 출력(가로·세로·거리), 허용 오차.
2. **정답을 독립적으로 만든다**: 테스트할 계산식과 같은 식으로 정답을 만들지 않는다(같은 실수를 하면 함께 맞아 버린다).
   - 윤곽 시선: 시선이 과일에 닿는지를 이차방정식으로 판정하고, 닿음과 안 닿음이 바뀌는 각도를 이분법으로 찾는다(`test/measure.test.js`의 `spheroidSilhouette`).
   - 사진: 화소마다 시선을 쏘아 과일·테이블과 만나는 점의 색을 칠한다(`test/scene.js`의 `render`).
   - 거리 정답: 카메라에서 과일 중심을 향한 선이 표면과 만나는 점까지(`trueSpheroidDistanceMm`).
3. **기본 장면부터 어려운 장면까지 넣는다**(아래 「장면 옵션」).
4. **실행한다**: `node test/measure.test.js`, `node test/detect.test.js`, `node test/app-flow.test.js`
5. **통과해도 숫자를 본다**: 처음부터 전부 통과하면 테스트가 너무 쉬울 수 있다.
   - 실제 오차(측정값/정답)를 한 번 찍어 허용 오차보다 충분히 작은지 확인한다.
   - 값이 정말 구분되는지 확인한다. 예: 비율을 틀리게 넣었을 때의 맞춤 오차가 화소 1개의 각도(약 1/fx 라디안)보다 커야 그 비율을 사진에서 찾을 수 있다. 작으면 그 조건(각도·거리)은 앱에서 막거나 안내한다.
   - 확인용 출력은 테스트에 남기지 않는다.
6. **실패 조건도 테스트한다**: 계산하면 안 되는 입력이 `null`이나 오류(`none`, `cut`, `small`)로 끝나는지 본다.

## 예시

[예시] 「AR에서 지름 70mm 과일을 45도로 보면 크기와 거리가 3% 안에서 다시 나온다」를 확인하는 테스트

```js
test("AR 45도: 크기·거리 3% 이내", () => {
  const opt = spheroidArScene(0.035, 0.035, 45, { noise: 8, shadow: true }); // 입력: 정답을 아는 장면
  const found = detectFruitSpheroid(render(opt), seedFor(opt), opt.k, opt.pose);
  const cam = [opt.pose[12], opt.pose[13], opt.pose[14]];
  const m = measureSpheroidCone(found.cone, found.s, cam, 0);              // 출력: 계산한 크기·거리
  assert.ok(relErr(m.widthMm, 70) < 0.03, `크기 ${m.widthMm.toFixed(1)}mm`);
  assert.ok(relErr(m.distanceMm, trueSpheroidDistanceMm(opt)) < 0.03);     // 정답은 계산식과 따로 구함
});
```

출력 예: `ok   AR 45도: 크기·거리 3% 이내`. 처음 통과하면 실제 값(예: 「크기 69.8/70.0」)을 한 번 찍어 본 뒤 그 출력은 지운다.

# 배포 페이지 검토

이 앱은 폰의 AR(WebXR)이 있어야 측정 화면이 뜬다. PC에서는 첫 화면에 「AR 미지원」만 보이므로, 배포 페이지에 가짜 AR 프레임을 넣어 측정 화면을 띄우고 확인한다. 실제 카메라·AR 동작(초점, 위치 추적, 손떨림)은 확인할 수 없으니 [폰] 항목으로 사용자에게 맡긴다.

## 순서

1. **배포 반영 기다리기**: push 뒤 GitHub Pages가 바뀌는 데 1~2분 걸린다. 이번에 새로 넣은 함수 이름이 배포 파일에 보일 때까지 10초 간격으로 확인한다.
   ```
   for i in $(seq 1 15); do n=$(curl -s "https://lgosoup.github.io/fruit-measure/app.js?x=$RANDOM" | grep -c 새함수이름); [ "$n" -gt 0 ] && break; sleep 10; done
   ```
2. **배포 파일과 커밋 비교**: `index.html`, `app.js`, `measure.js`, `detect.js`, `style.css`를 받아 `git show HEAD:파일`과 같은지 본다(줄바꿈 `\r`은 지우고 비교). 다르면 배포가 아직이거나 캐시다.
3. **크롬으로 열기**: 브라우저 도구로 새 탭에 `https://lgosoup.github.io/fruit-measure/?r=단계번호`를 연다. 처음 화면이 「AR 미지원」이고 콘솔 오류가 없는지 본다.
   - 주소 뒤 쿼리는 페이지에만 붙어 **스크립트 캐시는 피하지 못한다.** 이번에 넣은 함수가 페이지에 있는지(`typeof 새함수이름`) 먼저 보고, 없으면 아래를 실행한 뒤 다시 확인한다(그냥 새로고침으로는 안 바뀐다).
     ```js
     await Promise.all(["measure.js", "detect.js", "app.js", "style.css", "index.html"].map((f) => fetch(f, { cache: "reload" })));
     location.reload();
     ```
4. **가짜 AR 넣기**: `scripts/fake-ar.js` 내용을 페이지에서 그대로 실행한 뒤, `window.fakeAr`로 장면을 넣는다.
   ```js
   await fakeAr.start();
   fakeAr.approach(0.42, 0.22, 14);   // 다가가며 크기 확정
   fakeAr.surface(16);                // 표면까지 16cm
   fakeAr.state();                    // 안내·거리·크기·버튼 상태
   ```
5. **캡처와 숫자 확인**: 확인할 상태마다 화면을 캡처하고(디스크에 저장), `state()` 숫자를 정답과 비교한다. 가짜 과일은 지름 70mm, `surface(cm)`의 정답 거리는 그 cm다.
6. **콘솔 오류 확인**: 오류만 골라 읽는다. 없으면 「콘솔 오류 없음」으로 보고한다.
7. **기록**: todo의 [AI 검토] 항목 아래에 「- 결과: …」로 확인한 상태와 숫자를 적고 체크한다. 캡처 경로는 사용자에게 알린다. 탭은 닫는다.

## 예시

[예시] 16단계(12cm 안내) 검토

```js
await fakeAr.start();
fakeAr.approach(0.42, 0.22, 14);   // → { size: "69.1", done: true, ... }
for (let cm = 20; cm >= 16; cm--) fakeAr.surface(cm);
fakeAr.state();                    // → { distance: "표면까지 15.9 cm", guide: "촬영하려면 4cm 더 가까이 다가가 주세요", inside: false }
for (let cm = 15; cm >= 10; cm--) fakeAr.surface(cm);
fakeAr.state();                    // → { distance: "표면까지 9.9 cm", guide: "12cm 안에 들어왔습니다. 촬영하세요", inside: true }
```

보고 예: 「16cm에서 15.9cm와 『4cm 더 가까이』, 10cm에서 초록 9.9cm와 『12cm 안』. 콘솔 오류 없음」

## 자주 나오는 경우

- **브라우저 도구가 연결되지 않음**: 1~2번(배포 반영, 파일 비교)만 하고, 화면 확인은 못 했다고 보고한다. [AI 검토] 항목은 체크하지 않는다. 사용자에게 확장 연결을 부탁한다.
- **둘레가 옆으로 늘어난 타원으로 보임**: 가짜 카메라 비율이 화면과 다를 때 생긴다. `fake-ar.js`는 화면 비율에 맞춰 만든다. 직접 프레임을 만들었다면 비율을 맞춘다.
- **장면을 한 번에 크게 바꾸면 놓침으로 나옴**: 앱은 크기·위치가 갑자기 바뀌면 다른 물체로 본다. 거리는 1cm씩 단계적으로 바꾼다(`surface`를 반복 호출).
- **자동 촬영 뒤 사진 화면에서 `createImageBitmap` 오류**: 가짜 카메라 이미지가 브라우저 `ImageData`가 아니면 생긴다. `fake-ar.js`는 `ImageData`로 감싸 돌려준다.
- **안내 문구가 바뀌지 않음**: 「놓쳤습니다」 같은 잠깐 안내는 3초 동안 다른 안내를 덮는다. 이어서 확인하려면 `arNote = null`로 지운 뒤 다시 본다.
- **사용자 폰에서 예전 화면이 보임**: GitHub Pages는 파일을 10분 캐시한다. 배포 파일이 커밋과 같으면 폰에서 새로고침하거나 잠시 뒤 다시 열어 달라고 안내한다.

## 8. 느낀 점, 결론

### 느낀 점

**1. 테스트 통과 뒤 폰에서 바뀐 측정 방식**

14단계의 처음 설계(폰을 30\~60° 비스듬히 들고 한 번에 가로·세로 재기)는 계산으로 그린 과일 장면에서 오차 1% 안쪽으로 테스트를 통과했다. 그런데 폰으로 직접 써 보니 각도를 맞추며 버튼을 누르기가 어렵고, 각도가 틀려도 안내가 없었다. AI는 정확도만 보고 사람이 쓰기 어려운 조건을 만들었다. 「과일을 화면 가운데 두고 다가가기만 하면 앱이 알아서 재면 된다」는 아이디어로 측정 방식을 바꿨고(C-7), 점 찍기·과일 인식 버튼도 없앴다. 이후로는 단계마다 [폰] 확인을 마지막 관문으로 두었다.

**2. AI가 넓히려 한 범위와 덜어낸 기능**

- 발전 방향을 고를 때 AI는 껍질 색 지수를 기록하자며 흰 종이로 색을 맞추자고 했다. 하지만 기준 물체를 매번 대는 것은 카드와 같아 현장에서 비현실적이고, 품종별 적정 색 기준도 없다. 최종 목표(당도·수확 적기)에 기여하지 않는 세부 목표는 오히려 방해라서 제외했다(C-3).
- 「과일이 위아래로 조금 납작하니 가로·세로를 따로 재자」고 계획했다가, 크기는 당도를 직접 알려 주는 값이 아니라 보정 값이라 일관된 지름 하나면 충분하다고 정리해 15단계를 통째로 취소했다(C-8).
- 「10cm에 맞춰 찍기」도 정확히 한 값일 필요는 없고 신호가 희석되지 않는 한도(12cm) 안이면 된다고 바꿨다(C-9). 가까운 쪽은 너무 가까우면 과일이 화면에 다 안 들어와 측정이 안 되는 것으로 충분해 하한을 두지 않았다.
- 결국 PRD 「왜 만드나요」에 캡스톤 주제와 기존 당도계와의 차이를 자세히 적은 뒤에야, 기능마다 얼마나 정밀해야 하는지를 판단할 기준이 생겼다.

**3. 폰에서만 드러난 문제**

- 「버튼이 가린다」는 말을 AI가 위쪽 버튼으로 짐작해 고쳤는데, 실제로는 크롬 안내가 아래쪽 버튼을 가리는 것이었다(C-10). 이후로는 화면 위치처럼 짐작이 갈리는 지적은 고치기 전에 어느 것인지 먼저 확인하기로 했다.
- 고쳤는데도 폰에서 예전 화면이 보였다. GitHub Pages가 파일을 10분 동안 캐시했기 때문이다. 「고쳤는데 안 바뀜」은 캐시부터 의심하게 됐다.
- 자동 촬영이 12cm에 들어오자마자 찍혔다(C-12). PC 테스트는 1cm씩 성큼 다가가는 장면이라, 사람이 천천히 다가오는 움직임을 만들지 못했다.
- 위에서 똑바로 찍자 사진 가운데의 꼭지를 과일로 잡아 거리가 440.9mm(실제 약 10cm)로 나왔다(C-13). 사진 가운데에서 윤곽을 찾는 코드는 처음부터 같았는데 예전에는 문제가 없었다. 자동 촬영이 「가운데에 두고 멈춘 순간」이라는 새 촬영 자세를 만들면서 드러난 것이다. 그 뒤로는 기능을 바꾸면 예전에 문제없던 부분도 새 사용 방식으로 다시 확인했다.
- 가까이 가면 카메라 화면이 흐려지는 것은 웹(WebXR)에서 초점을 바꿀 수 없는 한계라, 고치지 않고 한계로 기록했다.

**4. 재현한 뒤 고친 버그**

폰에서 나온 버그는 바로 고치지 않고, todo에 [버그 수정]과 변경 번호를 먼저 넣은 뒤 그 상황을 테스트 장면으로 만들어 **고치기 전 코드에서 실패하는 것**을 확인하고 고쳤다. 꼭지 문제를 재현한 「위에서 본 과일 장면」을 처음 과일을 찾는 단계에도 돌려 보니, 폰에서는 아직 드러나지 않은 같은 원인의 버그(크기 22.2mm / 실제 70mm)까지 나왔다(C-14). 재현 장면 하나를 관련 기능 전체에 돌려 보는 것이 유용했다.

**5. 바뀐 것을 기록하는 방식**

처음에는 todo 항목 옆에 원래 내용까지 적으려 했지만, 그러면 todo가 금방 길어진다. 그래서 바뀐 내용을 `changes.md`에 번호(C-1\~C-14)로 모으고, todo·PRD에는 `(구분 · 요약 / C-번호)`만 남겼다. 처음 계획과 비교하기 쉽고 시행착오(처음 시도한 방법과 버린 이유)도 한 곳에 남았다. 또 카드 기준 화면을 없앤 것은 우리 판단으로는 「AR이 기준을 대신한 것」이었지만 문서에 적지 않아, 평가자 시점 검토에서 「기능 축소로 보일 수 있다」는 지적을 받고 「기준 대체」로 기록했다(C-6).

**6. 스킬을 만든 시점과 다듬은 과정**

한 단계를 해 본 뒤 매번 반복되는 절차(단계 마무리, 제출 검토, 배포 페이지 검토)와 이 프로젝트에만 있는 지식(정답을 따로 만든 과일 장면 테스트)을 스킬로 묶었다. 그중 과일 장면 테스트가 가장 스킬다웠다. 다른 곳에서 가져올 수 없는 지식이고, 계산이 바뀔 때마다 그대로 다시 썼다. 스킬도 처음 실제로 쓰면 문제가 드러났다(배포 페이지 검토에서 스크립트 캐시, 가짜 이미지 형식). 스킬을 정식으로 부르지 않고 기억으로 진행하면 단계를 빠뜨리기도 했다.

**7. AI와 일하며 생긴 실수**

- 커밋 메시지를 고쳐 달라는 말을 AI가 커밋 승인으로 받아들여 바로 커밋했다가 되돌렸다. 세부 사항 승인과 실행 승인을 구분해, 메시지를 보여 주고 명시적인 지시를 받은 뒤에만 커밋하기로 했다.
- README에 「1\~6단계 … 7\~13단계」처럼 범위 표시 「\~」를 한 줄에 두 번 쓰자, GitHub가 그 사이를 취소선으로 그렸다. 편집기에서는 보이지 않고 GitHub 화면에서만 드러나, 사람이 화면을 보고 찾아냈다.

### 결론

이번 과제에서 가장 크게 느낀 것은 **기능의 가치를 정하는 기준은 최종 목표**라는 점이다. 이 앱의 목표는 근적외선 당도 측정에 필요한 거리와 크기를 현장에서 빠르게 얻는 것이다. 그래서 색 측정처럼 목표에 기여하지 않거나 기준 물체를 대야 하는 기능은 빼고, 가로·세로처럼 목적에 비해 과한 정밀도는 지름 하나로 줄였다. 대신 측정 흐름 자체를 바꾸는 데 집중했다. 「찍고 확인하기」를 반복하던 방식이 「다가가면 거리를 안내하고, 멈추면 찍는」 흐름이 됐고, 그 촬영 순간이 곧 근적외선을 재는 순간이 되도록 설계했다.

또 **모든 오류를 없애려 하기보다 다시 할 수 있게 만드는 것**이 현실적이었다. 실행 영상에서도 시작 직후 AR이 폰 위치를 잘못 잡아 크기가 100.5mm로 한 번 틀렸지만, 이건 AR이 어떻게 해도 가끔 생기는 오류다. 그래서 「크기 다시 재기」, 「다시 선택하기」, 「다시 찍기」가 있고, 영상에서도 다시 재서 49.1mm로 이어 측정했다. 가까이서 과일을 놓치거나 화면이 흐려지는 것도 같은 생각으로, 고칠 수 없는 한계는 기록하고 다시 하는 방법으로 대응했다.

바이브 코딩에서 AI는 계산식, 테스트 장면, 화면을 빠르게 만들고 검증했다. 하지만 무엇을 왜 재는지(PRD의 목적), 실제로 써 보니 어떤지(폰 확인), 무엇을 덜어낼지는 사람이 정했다. 측정 방식을 바꾼 결정적인 아이디어(다가가며 크기 재기, 화면 가운데 자동 선택, 크기는 보정 값이라 지름 하나로 충분)는 사람이 직접 써 보고 낸 것이고, AI는 그것을 PRD → Todo → 테스트 순서로 빠르게 구현하고 확인했다. 다음 단계는 캡스톤에서 이 촬영 순간에 근적외선 센서 측정을 함께 실행하고, 크기·거리를 센서 기록과 함께 저장하는 것이다.
